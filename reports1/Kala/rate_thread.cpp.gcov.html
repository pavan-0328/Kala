      21             : /*
      22             :  Attitude Rate controller thread design.
      23             : 
      24             :  Rationale: running rate outputs linked to fast gyro outputs achieves two goals:
      25             : 
      26             :  1. High frequency gyro processing allows filters to be applied with high sample rates
      27             :     which is advantageous in removing high frequency noise and associated aliasing
      28             :  2. High frequency rate control reduces the latency between control and action leading to 
      29             :     better disturbance rejection and faster responses which generally means higher
      30             :     PIDs can be used without introducing control oscillation
      31             : 
      32             :  (1) is already mostly achieved through the higher gyro rates that are available via
      33             :  INS_GYRO_RATE. (2) requires running the rate controller at higher rates via a separate thread
      34             : 
      35             : 
      36             :  Goal: the ideal scenario is to run in a single cycle:
      37             : 
      38             :     gyro read->filter->publish->rate control->motor output
      39             : 
      40             :  This ensures the minimum latency between gyro sample and motor output. Other functions need 
      41             :  to also run faster than they would normally most notably logging and filter frequencies - most
      42             :  notably the harmonic notch frequency.
      43             : 
      44             :  Design assumptions:
      45             : 
      46             :  1. The sample rate of the IMUs is consistent and accurate.
      47             :     This is the most basic underlying assumption. An alternative approach would be to rely on
      48             :     the timing of when samples are received but this proves to not work in practice due to
      49             :     scheduling delays. Thus the dt used by the attitude controller is the delta between IMU
      50             :     measurements, not the delta between processing cycles in the rate thread.
      51             :  2. Every IMU reading must be processed or consistently sub-sampled.
      52             :     This is an assumption that follows from (1) - so it means that attitude control should
      53             :     process every sample or every other sample or every third sample etc. Note that these are
      54             :     filtered samples - all incoming samples are processed for filtering purposes, it is only
      55             :     for the purposes of rate control that we are sub-sampling.
      56             :  3. The data that the rate loop requires is timely, consistent and accurate.
      57             :     Rate control essentially requires two components - the target and the actuals. The actuals
      58             :     come from the incoming gyro sample combined with the state of the PIDs. The target comes
      59             :     from attitude controller which is running at a slower rate in the main loop. Since the rate
      60             :     thread can read the attitude target at any time it is important that this is always available
      61             :     consistently and is updated consistently.
      62             :  4. The data that the rest of the vehicle uses is the same data that the rate thread uses.
      63             :     Put another way any gyro value that the vehicle uses (e.g. in the EKF etc), must have already
      64             :     been processed by the rate thread. Where this becomes important is with sub-sampling - if 
      65             :     rate gyro values are sub-sampled we need to make sure that the vehicle is also only using
      66             :     the sub-sampled values.
      67             : 
      68             :  Design:
      69             : 
      70             :  1. Filtered gyro samples are (sub-sampled and) pushed into an ObjectBuffer from the INS backend.
      71             :  2. The pushed sample is published to the INS front-end so that the rest of the vehicle only
      72             :     sees published values that have been used by the rate controller. When the rate thread is not 
      73             :     in use the filtered samples are effectively sub-sampled at the main loop rate. The EKF is unaffected
      74             :     as it uses delta angles calculated from the raw gyro values. (It might be possible to avoid publishing
      75             :     from the rate thread by only updating _gyro_filtered when a value is pushed).
      76             :  3. A notification is sent that a sample is available
      77             :  4. The rate thread is blocked waiting for a sample. When it receives a notification it:
      78             :     4a. Runs the rate controller
      79             :     4b. Pushes the new pwm values. Periodically at the main loop rate all of the SRV_Channels::push()
      80             :         functionality is run as well.
      81             :  5. The rcout dshot thread is blocked waiting for a new pwm value. When it is signalled by the
      82             :     rate thread it wakes up and runs the dshot motor output logic.
      83             :  6. Periodically the rate thread:
      84             :     6a. Logs the rate outputs (1Khz)
      85             :     6b. Updates the notch filter centers (Gyro rate/2)
      86             :     6c. Checks the ObjectBuffer length and main loop delay (10Hz)
      87             :         If the ObjectBuffer length has been longer than 2 for the last 5 cycles or the main loop has
      88             :         been slowed down then the rate thread is slowed down by telling the INS to sub-sample. This
      89             :         mechanism is continued until the rate thread is able to keep up with the sub-sample rate.
      90             :         The inverse of this mechanism is run if the rate thread is able to keep up but is running slower
      91             :         than the gyro sample rate.
      92             :     6d. Updates the PID notch centers (1Hz)
      93             :  7. When the rate rate changes through sub-sampling the following values are updated:
      94             :     7a. The PID notch sample rate
      95             :     7b. The dshot rate is constrained to be never greater than the gyro rate or rate rate
      96             :     7c. The motors dt
      97             :  8. Independently of the rate thread the attitude control target is updated in the main loop. In order
      98             :     for target values to be consistent all updates are processed using local variables and the final
      99             :     target is only written at the end of the update as a vector. Direct control of the target (e.g. in
     100             :     autotune) is also constrained to be on all axes simultaneously using the new desired value. The
     101             :     target makes use of the current PIDs and the "latest" gyro, it might be possible to use a loop
     102             :     delayed gyro value, but that is currently out-of-scope.
     103             : 
     104             :  Performance considerations:
     105             : 
     106             :  On an H754 using ICM42688 and gyro sampling at 4KHz and rate thread at 4Khz the main CPU users are:

     125             :  So we get almost a halving of CPU load in the rate and rcout threads. This is the main way that CPU
